# power-health — нотатки для Claude

Telegram-бот, що пише в канал, коли вдома зникає / з'являється світло. Детектор — Android-телефон на зарядці
(MacroDroid шле стан зарядки), сервер — Cloudflare Worker + D1, сповіщення — Telegram-канал. Усе безкоштовно,
статична IP не потрібна (телефон і Telegram самі ходять до Worker'а).

Користувач спілкується українською; уся видима користувачу мова бота — українська.

> Репозиторій **публічний**. Ніколи не комітити секрети (`.env`), домашню адресу, Telegram ID власника чи ID каналу.
> Вони живуть лише в секретах Cloudflare і в D1.

## Архітектура

```
MacroDroid ──POST /device/event|heartbeat (X-Device-Key)──► Worker ──► D1 (state, periods)
Telegram   ──POST /telegram (X-Telegram-Bot-Api-Secret-Token)─►  │  ──► Telegram API (канал, ЛС власника)
cron */5   ──scheduled()──────────────────────────────────────►  │  ──► SvitloPulse API, сайт ДТЕК
curl       ──POST /admin/setup (Bearer WEBHOOK_SECRET)────────►  └ setWebhook + меню команд
```

| Файл | Що |
|---|---|
| `src/index.ts` | Маршрути, `makeCtx`, `scheduled` |
| `src/device.ts` | Звіти телефона → переходи стану, сповіщення «світло зникло/з'явилось», стирання блимань |
| `src/bot.ts` | Команди в ЛС власника, `/activate` у каналі, вихід із чужих чатів |
| `src/cron.ts` | Детектор офлайн, нагадування про паузу, оновлення повідомлення ДТЕК, звіти, попередження, графік на завтра, закріплений статус |
| `src/state.ts` | Стан (один рядок), `switchMode`, періоди, `summarize` |
| `src/stats.ts` | `/stats`, тижневий і місячний звіти |
| `src/schedule.ts` | SvitloPulse: графік черги, `/history/plan`, тексти попереджень і графіка на завтра |
| `src/dtek.ts` | Сайт ДТЕК: дані по адресі (CSRF-флоу) |
| `src/outage-message.ts` | «🔴 Світло зникло» по частинах + редагування, коли ДТЕК оновив дані |
| `src/status-message.ts` | Закріплене повідомлення «що зараз», `inBackground` |
| `src/format.ts` | Тривалості, час за Києвом, північ/DST |
| `test/helpers.ts` | D1 на `node:sqlite`, фейкові Telegram / SvitloPulse / ДТЕК |

`Ctx` = `{ env, db, tg, http, now, defer? }`. `tg`, `http`, `now` підміняються в тестах; `defer` — це `waitUntil`
(у тестах відсутній → фонові задачі виконуються синхронно).

## Модель даних

- `state` — один рядок `id = 1`. `mode`: `on | off | paused | NULL` (невідомо), `mode_since` — початок поточного
  періоду (ms), `mode_since_approx` — час відновлено з heartbeat (показуємо «≈»).
- `periods` — історія `on/off/paused`; поточний має `end_ts = NULL`. `switchMode` атомарно закриває і відкриває (batch).
- Усі часи — ms UTC. Час від телефона (`ts`) приходить у секундах (`{system_time}`), сервер приймає і с, і мс;
  невалідний або з майбутнього → час сервера.
- Звіти телефона впорядковуються за `phone_ts`: якщо `ts <= phone_ts` — це повтор/запізнення, стан не змінюємо.
- Кожна зміна схеми — **нова міграція** (`migrations/000N_*.sql`): база вже в проді.

## Рішення користувача (не міняти без запиту)

- **Сповіщення миттєві**, без затримки на «мигання». Натомість відключення коротші за `BLIP_MAX_MIN` (5 хв)
  **стираються**: видаляємо «🔴 Світло зникло» з каналу, не шлемо «з'явилось», склеюємо періоди. Винятки: не вдалося
  видалити повідомлення, або перед відключенням не було періоду «on» — тоді звичайна обробка.
- **Тривалості — лише години й хвилини**, без днів: «33 год 53 хв». Кінець доби — «24:00», не «06.11 00:00».
- **Керування — лише власник** (`OWNER_USER_ID`) в особистому чаті з ботом. Адмінів немає (були, прибрали: власник
  обмежує доступ у BotFather через restricted bot usage). Повідомлення інших ігноруються мовчки.
- **Канал** активується командою `/activate`, написаною **в самому каналі**. Перевірка: `post.from` = власник, а якщо
  допис від імені каналу (без `from`) — `getChatMember` власника має бути `creator`. Бот видаляє допис `/activate`.
  З груп і каналів, куди його додав не власник, бот виходить.
- **Куди що йде**: у канал (там є підписники — не спамити!) — лише світло, звіти, попередження, графік на завтра,
  закріплений статус. В ЛС власника — усе про детектор («не на зв'язку», «знову на зв'язку», «детектор підключено»),
  відповіді на команди, нагадування про паузу, проблеми з правами/каналом.
- **Пауза** (`/pause`) — не записуємо відключення і не шлемо нічого, включно з «детектор офлайн». `/resume` — лише
  якщо телефон зараз на зарядці. Нагадування власнику через 1 год, далі кожні 3 год.
- **Детектор офлайн**: тиша > `OFFLINE_AFTER_MIN` (45 хв; heartbeat раз на 15 хв) → одне попередження власнику; при
  поверненні — «знову на зв'язку». Якщо після офлайну стан змінився, пишемо **час, коли детектор повернувся**
  («🟢 Світло з'явилось о 04:42» + «ℹ️ Детектор був без зв'язку…»), а не вікно «приблизно між 02:30 і 04:42».
  Вікно «між … і …» лишається лише для загубленої події при справному зв'язку (кілька хвилин).
- **Прогнозів не робимо самі** (користувач явно відмовився). Час відновлення — лише з ДТЕК по адресі (пріоритет) або
  з графіка SvitloPulse. Під час аварійних — «час відновлення невідомий».
- **Статистика**: головна метрика — % часу зі світлом **від відстеженого часу** (без пауз і часу без даних). Дні й
  місяці без даних пропускаємо. Стрілки ↑/↓ — різниця ≥ 2 п.п. Частота «N відкл. (0,8/добу)», мала — «<0,1».
- **Звіти**: тижневий — понеділок 10:00 за Києвом, повний минулий тиждень Пн–Нд; місячний — 1-го о 10:00, 12
  завершених місяців. Cron кожні 5 хв дивиться місцевий час (DST!), дата останнього звіту в `state` — від дублів.
  Без даних звіт не шлемо.
- **Попередження** за ~30 хв до відключення за графіком — лише коли світло є і графік діє (не `emergency`), один раз
  на інтервал (`warned_outage_start`). Якщо інтервал закінчується опівночі, а графіка на завтра ще немає (ДТЕК
  публікує його ~21:15, попередження о 21:00 — реальний випадок), пишемо «ℹ️ Можливо, й довше: графік на завтра ще не
  опублікований», а коли графік з'явиться — **редагуємо** попередження (`warn_*` у state; «через ~N хв» рахується від
  `warn_sent_at`, тож не змінюється). Та сама примітка — у «📅 За графіком» і в закріпленому статусі.
- **Графік на завтра** — з 22:00 (ДТЕК публікує після ~20:00), перевіряємо кожні 5 хв до кінця доби, шлемо лише
  статус `applies`, один раз (`tomorrow_sent_date`). Шкали з % тут немає — пробували, користувачу вийшло неінформативно.
- **Шкали** — `■■■■■■■■□□` (окремі квадрати; `█░` зливались у смугу). У статистиці таблиці днів і місяців — у
  `<pre>` (моноширинний шрифт), мітка рядка завжди 8 символів («Вт 03.11», «Лис 2026»), щоб шкали стояли рівно одна
  під одною; змінний текст («сьогодні, до 10:00», «дані за N дн.», деталі місяців) — поза таблицею. Рядок таблиці
  ≤ ~35 символів, щоб не переносився на телефоні.
- **Закріплене повідомлення** зі станом: тихе, оновлюється cron'ом і одразу після змін стану; якщо видалили —
  створюється нове (помилка `message to edit not found`); відкріплення бот не бачить. Службове «закріплено» бот
  видаляє. Для закріплення в каналі потрібне право «Редагувати повідомлення інших».
- **Відкинуті ідеї**: власний статистичний прогноз; userbot/MTProto для читання бота ДТЕК; MacroDroid-перехоплення
  сповіщень бота ДТЕК («важко і не стабільно»); `/pin off` поки не потрібен.

## Зовнішні джерела

### SvitloPulse (графіки + ознака аварійних)
- База `https://svitlopulse.andrewboyko.name/api/v1`, без ключа, ліміт 600 читань/хв з IP. Неофіційний, ймовірно
  одна людина — усе має працювати, якщо він упаде (таймаут 4 с, рядок просто не додається).
- `GET /groups/{operator}/{group}` → `group.{state, class: planned|emergency|..., plan_status: applies|emergency,
  restore_at, today[], tomorrow[]}`; інтервали `{start, end, kind: off|maybe}` з офсетом +02:00/+03:00.
  Невідома черга → 404.
- `GET /history/plan/{operator}/{group}?date=YYYY-MM-DD` → `schedule.status` `applies` (зі `slots`) / `emergency`;
  **404 = ще не опубліковано**. `tomorrow: []` у `/groups` неоднозначне — для графіка на завтра використовуємо `/history/plan`.
- Київ = оператор `dtek-kem`, 60 черг `1.1…60.1` (`SCHEDULE_OPERATOR`). Суміжні інтервали склеюємо через північ.
- Банер «ДЕМО-ДАНІ» на сторінці документації — лише там; API віддає `demo: false`.

### Сайт ДТЕК (дані по адресі — найточніше джерело)
- `https://www.dtek-kem.com.ua` (`DTEK_SITE`). Сторінки (GET) закриті Incapsula, але **POST `/ua/ajax` антибот не
  перевіряє**. Механізм узято з github.com/NetZhizni/ha-dtek-krem-outages (`api.py`).
- CSRF Yii2: перший POST без токена → 400 + cookie `_csrf-dtek-kem` (підписаний, не зашифрований; токен —
  PHP-серіалізований `i:1;s:N:"TOKEN"`). Далі `X-CSRF-Token: base64url(mask + mask XOR token)` + cookie.
- `method=getHomeNum`, `data[0][name]=street`, `data[0][value]=<вулиця як на сайті>`, `data[1][name]=updateFact`,
  `data[1][value]=` → `{result: true, data: {"<будинок>": {sub_type, start_date, end_date, sub_type_reason}}}`.
  `sub_type` — причина («Стабілізаційне відключення (Згідно графіку погодинних відключень)», аварійне…), порожній —
  відключення немає. Дати `"HH:MM dd.mm.YYYY"` за Києвом. `sub_type_reason: ["GPV20.1"]` → черга.
  Невідома вулиця → `{result: false, text: "Error"}`.
- Ключі будинків бувають `12/14`, `74А`, `37-41` — шукаємо з нормалізацією (`-` ≡ `/`, регістр, пробіли).
- `method=getStreets` → масив ~2500 вулиць (для підказок у `/address`).
- Перевірено: працює з мережі Cloudflare (`wrangler dev --remote`), запис збігся з повідомленням бота ДТЕК.
- ДТЕК часто реєструє відключення на кілька хвилин пізніше → поки світла немає, cron перепитує й **редагує**
  «🔴 Світло зникло» (зберігаємо частини в `off_parts`, дані ДТЕК у `off_dtek`, показуємо «(було 18:30)» при перенесенні).
  Запис, що почався > 60 хв до нашого відключення, — старий, ігноруємо.
- Якщо через 15 хв після зникнення світла ДТЕК **успішно відповідає**, але відключення за адресою не бачить — дописуємо
  «⚠️ ДТЕК не бачить відключення за адресою. Можливо, проблема в будинку чи квартирі.» (`off_parts.dtekMissing`).
  Коли ДТЕК пізніше зареєструє — примітку замінюють його дані. Сайт не відповів — нічого не пишемо.
- `start_date` у ДТЕК, схоже, — фактичний час вимкнення (збігся з детектором до хвилини, а графік — ні).
- Будинок може мати дві лінії (вводи) у різних чергах: тоді `sub_type_reason` містить дві групи, але під час
  стабілізаційного відключення ДТЕК показує лише групу, за якою вимкнено. Для нашого будинку поки бачили тільки 20.1
  (дивились лише під час відключень); «Київ Цифровий» каже про лінії 1 і 2. У Києві груп «X.2» зараз немає (60 груп X.1).

### Розглянуті й не взяті
- svitlo.live / `svitlo-proxy.svitlo-proxy.workers.dev` — графіки всіх областей, про аварійні не знає.
- `dtek-api.svitlo-proxy.workers.dev` — графіки + регіональний прапорець `emergency`, без адреси.

## Телефон (реальне налаштування)

- Xiaomi: Батарея → «Без обмежень»; застосунок «Безпека» → «Автозапуск» → MacroDroid; замок у недавніх.
- **Телефон має бути у звичайній розетці**, не через ДБЖ / павербанк / ноутбук — інакше завжди «на зарядці».
  Роутер вдома на ДБЖ (10–12 год), далі телефон іде через мобільні дані.
- Макрос **Heartbeat**: тригери «Регулярний інтервал 15 хв» + «Завантаження пристрою»; дії — `If Power Connected` →
  HTTP Request POST `/device/heartbeat`, заголовок `X-Device-Key`, тіло
  `{"charging": true, "ts": "{system_time}", "battery": "{battery}"}`; другий `If` (відключено) → те саме з `false`.
  (`Else` в інтерфейсі не знайшовся — тому два `If`.)
- Макрос **Подія живлення** — клон Heartbeat з тригерами Power Connected/Disconnected і URL `/device/event`.
- HTTP Request у MacroDroid — у розділі **Web Interactions** (не Connectivity). `{system_time}` — секунди, перевірено.
- Повторних спроб у макросах немає: загублену подію виправляє heartbeat (повідомлення позначається «приблизно між…»).
- ⚠️ `docs/macrodroid.md` застарів (описує 3 макроси з повторами) — треба оновити під налаштування вище.

## Розробка і деплой

```bash
npm test            # vitest; D1 = node:sqlite з тими ж міграціями
npm run typecheck
npm run db:migrate  # wrangler d1 migrations apply power-health --remote
npm run deploy
```

- **Порядок**: міграція на remote → **перевірити** `npx wrangler d1 migrations list power-health --remote`
  («No migrations to apply») → `deploy`. Одного разу `apply` у неінтерактивному режимі мовчки не застосувався.
- Після зміни команд, webhook-секрету чи `OWNER_USER_ID`:
  `curl -X POST https://power-health.power-health.workers.dev/admin/setup -H "Authorization: Bearer $WEBHOOK_SECRET"`
  (робить `drop_pending_updates`, оновлює меню команд лише для чату власника).
- Секрети: `.env` (у `.gitignore`) → `npx wrangler secret bulk .env`. Звичайні змінні — `vars` у `wrangler.jsonc`.
- Перевірити вихідні запити саме з мережі Cloudflare: тимчасовий воркер + `wrangler dev --remote`.
- Логи проду: `npx wrangler tail`. Стан: `npx wrangler d1 execute power-health --remote --json --command "SELECT * FROM state"`.

### Тести
- `test/helpers.ts`: `createD1()` — `node:sqlite` через `createRequire` (щоб Vite не бандлив), усі міграції.
- Фейковий Telegram: `sendMessage` повертає `message_id`; `sent()` — сповіщення в канал **без** тихих
  (`disable_notification` = закріплений статус); `dm()` — ЛС власника; `failing` / `failWith` / `failSendTo`.
- Фейковий `http`: SvitloPulse (`groups`, `plans`, `scheduleDown`) і ДТЕК з повним CSRF-флоу (`dtekStreets`, `dtekDown`).
- `T0` = 05.11.2026 10:00 за Києвом. Тести, що стрибають у часі, мають тримати `last_seen` свіжим, інакше cron
  слушно пише «детектор не на зв'язку».
- Перша зміна стану створює закріплений статус — тести, що перевіряють його створення, скидають `status_message_id`.

## Робочі прийоми (прод)

- **Очистити історію**, лишивши налаштування (канал, адресу, чергу): `DELETE FROM periods` + скинути в `state`
  поля режиму, телефона, `off_*`, звітів, попереджень, `status_*` (див. історію: так робили перед запуском, додавши
  одне відключення вручну).
- **Очистити канал**: id повідомлень у каналі послідовні → `deleteMessages` діапазоном (пачки по 100); якщо пачка
  падає — по одному. №1 (службове «канал створено») не видаляється.
- **Відредагувати старе повідомлення** (бот не зберігає id і не читає історію): тихо `forwardMessage` кандидатів у ЛС
  власника, прочитати `text`, видалити копію, потім `editMessageText`.
- Перевірити чергу / дані ДТЕК вручну — локальний скрипт із тим самим CSRF-флоу (див. `src/dtek.ts`).

## Стиль

- Тексти для людей — українською; апостроф `'` (не `’`). Обережно з `sed` по рядках у одинарних лапках:
  заміна `’`→`'` колись зламала JS-рядки.
- Коментарі в коді — українською, пояснюють «чому».
- Сповіщення — простий текст (без `parse_mode`). Виняток — `/stats` і звіти: `parse_mode: 'HTML'` заради `<pre>`;
  увесь текст там екранується (`escapeHtml`; напр. «<0,1/добу» → `&lt;`).
